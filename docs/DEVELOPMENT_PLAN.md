# 开发计划：自动转谱与工作区重构

版本：1.0 · 2026-10-23  
依据：[PRD](PRD.md) / [技术设计](TECHNICAL_DESIGN.md) / [UI 设计](UI_DESIGN.md)  
状态：实施中。实际完成情况见下方执行记录；本计划不指定未经评估的发布日期。

执行更新（2026-10-23）：已在 `codex/automated-workspace` 开始实施，新界面遵循用户追加的日系清新风。各项交付、验证与未完成验收见 [实施记录](IMPLEMENTATION_STATUS.md)；本计划保留为原任务清单，不将部分实现自动等同于正式发布完成。

## 1. 交付目标

用户选择视频 / PDF、谱面区域和类型后，一次启动即可自动整理、识别、补读、局部复核及获取 GP5 草稿。界面采用低饱和、多区域的工作台，人工按疑点校对。保持两类谱面读取能力和人工修改安全。

采用小步交付：先固定数据与接口，再交付可浏览的新工作区，随后接入自动流程，最后做实际识谱质量与发布验收。UI 与读取算法分开提交，便于判断问题来源和回退。

## 2. 版本与实施约束

- 以 `v0.2.0-preview.1` 为已发布基线；当前文档保留在试用工作区。
- 开始实现时创建 `codex/automated-workspace` 分支，保留原主分支及标签；此名称为计划，当前尚未创建。
- 原始素材、已有 GP5 和用户在外部修正的文件不参与覆写；测试仅用独立副本或授权样本。
- 每阶段产出独立提交与变更说明，功能开关支持旧工作区回退；新数据不强行交给旧模型读取。
- 除非用户进一步要求，本计划不包含立即发布、合并主分支或上传私人材料。

## 4. 分批交付与完成定义

### M1：安全的数据基础（T01–T03）

交付版本模型、迁移和基准记录。通过旧项目、重复迁移、保存冲突及人工保护检查。未通过前不改造破坏性准备入口，不拿真实项目验证覆盖操作。

### M2：可评审的新工作区（T04–T05）

交付低饱和主题、准备画布、横向视图导航、设置抽屉及结果布局骨架。使用只读数据展示空态、处理中和结果态；记录 1366 / 1440 / 1920 宽度及缩放截图。此阶段可以评审设计，但不能宣称新自动流程已完成。

### M3：一次启动与基础草稿（T06–T08、T10–T11 的基础部分）

打通输入→本地识别→校验→草稿；任务可取消 / 恢复，草稿不依赖低分或核对全通过。首先交付实际可用闭环，再接入自动补读 / 模型。

### M4：自动复核与集中校对（T09、T11 完整版、T12）

按疑点自动补读 / 复核，原版本与基础草稿仍保留。交付同屏证据与编辑、问题导航、保存保护、版本选择。无模型时主要流程照常可用。

### M5：质量改进与发布候选（T13–T16）

完成专项识谱修复、缓存与预算校准；用未参与调试的样例验证。实际核对 GP5 后整理发布候选和回退说明。是否合并及发布按后续用户指令执行。

## 5. 验收场景

| 场景 | 必须观察到的结果 |
| --- | --- |
| 新视频 / 纯 TAB | 框区域、选类型后一次启动，可下载草稿 |
| 新 PDF / 联合谱 | 页面预览、区域确认后处理；无视频不尝试补读 |
| 低 OCR 分但音符可写 | 草稿可下载；提示定位具体拍位 |
| 存在缺失 / 时值未知 | 已知音保留，缺失清晰标记，不伪称节奏准确 |
| 模型未配置、不可用或超时 | 有界结束；保留本地结果，不无限等待 |
| 同一疑点多次修改 | 记录候选与接受理由，不能绕过人工保护 |
| 自动复核仍在运行 | 已发布基础草稿可下载，标明版本 |
| 同时编辑与任务完成 | 编辑被保留；任务结果独立，活动指针不静默切换 |
| 双击开始 / 重复请求 | 不启动重复写任务，返回同一活动任务 |
| 取消 / 服务重启 | 保存检查点；状态可解释；重试不重复应用补丁 |
| 切换项目 / 版本 | 旧请求不覆盖新页面；未保存修改得到处理 |
| 旧项目迁移 / 失败 / 回退 | 原文件不变；可重复导入；旧下载可访问 |
| 跨行、印刷编号、边缘截断 | 无凭空丢小节；冲突有来源证据 |
| 延音、10→0、误判休止 | 独立回归样例核对，并记录剩余限制 |
| 界面操作与键盘 | 主要操作易找，焦点可见，谱面与疑点可同屏阅读 |
| GP5 及报告 | 往返验证通过，实际 Guitar Pro 核对，疑点与标记对应 |

每项记录输入版本、配置、结果版本、预期 / 实际及证据。实际 Guitar Pro 核对若需要人工执行，应明确记为待验证，不能用程序往返读取替代。

## 6. 验证与代码检查安排

- 数据与任务层：针对版本保护、迁移、幂等、取消、恢复及补丁接受写有意义的测试。
- 算法层：每次专项修改只先跑相关样例；完成后跑原有完整回归，避免纯 TAB 被联合谱修改影响。
- 前端：类型检查、生产构建；新异步逻辑与编辑冲突有交互验证，排版主要使用浏览器截图检查。
- 发布前：统一端到端验证、实际 GP5 核对、源码 / 发布包隐私检查和安装验证。
- 测试失败先定位再修复；不为追求指标隐藏疑点、提高未经校准的分数或改写验收样本答案。

## 7. 性能与质量评估

固定机器、输入和配置，分别记录冷运行与缓存运行。比较人工额外点击、每百小节修正拍位、自动修复引入新错、缺失 / 重复数量及阶段耗时。

准确率、速度和模型预算的最终数值在 T01 基准与 T14 实测后填写；不把本机一次成功的样例当作所有输入保证。若自动化减少点击却增加人工修正，不能判为完成目标。

## 8. 变更与停止条件

出现人工修改被覆盖、旧文件损坏或任务越过版本冲突保护时，暂停新流程发布，先修复并验证数据保护。若局部模型引入错误且无法可靠过滤，关闭该自动补丁路径，保留人工可查看的建议及本地草稿，不阻断其他阶段交付。

超出四弦贝斯 / 两类谱面、直接写新版 GP、外部谱修改合并等需求需单列后续范围，不穿插扩大当前交付。开发中若需调整三份设计的关键决策，同步记录原因、影响任务及新的验收方式。

## 9. 文档维护

开发以本计划任务 ID 跟踪，完成项补充提交与验收记录。PRD 定义目标，技术文档定义实现约束，UI 文档定义布局与交互；三者冲突时先更新设计记录，不以局部实现默默改变用户已确认的默认流程。
